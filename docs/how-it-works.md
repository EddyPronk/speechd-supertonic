# How it works

Firefox (Reader View "Narrate" and the Web Speech API) speaks through
speech-dispatcher. speechd-supertonic plugs Supertonic TTS into speech-dispatcher
with its `sd_generic` module, which runs a shell command for every utterance. A
small server keeps the Supertonic model loaded, so speech starts quickly.

```
Firefox ─► speech-dispatcher ─► sd_generic runs, per utterance:
                │                 printf text | supertonic_say.py ─► pw-play
                │                                     │
                │                         Unix socket │ JSON request in,
                │                                     │ raw audio streamed out
                │                                     ▼
                │                 supertonic_server.py  (model stays loaded,
                │                 supertonic-tts.service, started by systemd)
                │
                └─► espeak-ng (backup; used automatically after a failed utterance)
```

Statements marked *verified* were checked on the setup listed in the README
("Tested with"), by hand or by the automated tests in `tests/`.

## Installed files

| File | What it does |
|------|--------------|
| `~/.local/share/speechd-supertonic/supertonic_server.py` | The server: loads the model once, synthesizes requests, streams float32 PCM back. Runs with `uv run --script`, which installs its Python dependencies in a cached environment. |
| `~/.local/share/speechd-supertonic/supertonic_say.py` | Client run by speech-dispatcher: text on stdin, gets the audio from the server and plays it with `pw-play`. Plain `python3`, standard library only, so it starts instantly. |
| `~/.local/share/speechd-supertonic/speechd_timing.py` | Timing summary per utterance from the log (see [Logging](#logging)). |
| `~/.config/systemd/user/supertonic-tts.socket` | Owns `$XDG_RUNTIME_DIR/supertonic-tts.sock` (mode 0600) and starts the service on the first request. Enabled at login. |
| `~/.config/systemd/user/supertonic-tts.service` | Runs the server. |
| `~/.config/speech-dispatcher/modules/supertonic.conf` | sd_generic config: the pipeline, rate/volume pass-through, UTF-8, voice list. Generated by `install.sh`. |
| `~/.config/speech-dispatcher/speechd.conf` | A block between `# >>> speechd-supertonic` and `# <<< speechd-supertonic` loads `supertonic` (as the default) and `espeak-ng`. |
| `~/.cache/speechd_supertonic.log` | Log of every request (see [Logging](#logging)). |
| `~/.cache/supertonic3/` | The downloaded model (about 400 MB). |

A `speechd.conf` in `~/.config` **replaces** `/etc/speech-dispatcher/speechd.conf`
rather than adding to it. That's why `install.sh` starts from a copy of the
system file when you don't have one yet. As soon as it has an `AddModule` line,
auto-detection is off, so every module you want must be listed there; the
installer adds `espeak-ng` next to `supertonic`.

## The pipeline

sd_generic runs this for each utterance, with `/bin/bash` and `set -o pipefail`
in front (simplified; the real line also quotes the paths):

```
printf %s '$DATA' | supertonic_say.py --voice '$VOICE' --lang '$LANGUAGE' \
                        --rate $RATE --volume $VOLUME 2>>~/.cache/speechd_supertonic.log
```

The client starts `pw-play --raw --format f32 --rate 44100 --channels 1 -` itself
and feeds it the audio, so the command's exit status is the client's:

| Situation | Client exits | What speech-dispatcher does |
|-----------|--------------|-----------------------------|
| Played to the end | 0, logs `[player] INFO playback finished` | Reports the end of the utterance; Narrate sends the next one. |
| Stopped or skipped (speech-dispatcher kills the client) | killed | Normal stop: the utterance ends at once, the player is killed with the client, and the module keeps working. *Verified (end-to-end test).* |
| Server unreachable; server reports an error (also after part of the audio was played); connection closed before the end of the utterance; player fails or stops reading early | 1, error in the log, no `playback finished` | sd_generic logs "We failed to speak, kill ourself" and exits. speech-dispatcher sends **no** end event for that utterance (Narrate waits until you press stop), and uses eSpeak NG for everything after it until speech-dispatcher restarts. *Verified (end-to-end test, speech-dispatcher 0.12.0).* |

Before this was fixed, the command ended with a separate `printf` that logged
"playback finished", which hid failures: a dead server meant silent
"successful" utterances.

- **Quoting matters.** `$DATA` is the text from the web page. sd_generic escapes
  single quotes in it, so it must be wrapped in single quotes (`\'$DATA\'` in the
  config file). With double quotes a page could run shell commands, for example
  `speechSynthesis.speak(new SpeechSynthesisUtterance("$(id)"))`.
- **Whole paragraphs go to the server.** Narrate sends one HTML element at a time
  (a paragraph, a heading, a list item) and waits for it to finish. By default
  sd_generic would then split it at sentence ends and wait for each sentence to
  finish *playing* before synthesizing the next, so every sentence paid its full
  synthesis time as silence (1–3s). `GenericMaxChunkLength 100000` and
  `GenericDelimiters ""` turn that off.
- **The server synthesizes ahead.** It splits the paragraph into sentences and
  synthesizes sentence n+1 while sentence n plays (synthesis runs at about
  25–30% of real time). Each sentence is synthesized in one call, so its
  intonation stays intact. Splitting at a comma to start sooner was tried and
  dropped, because the cut was audible.
- **Sending runs in a separate thread**, because a socket write blocks until the
  player has room, which for a long sentence is nearly the end of its playback.
  Synthesizing after each write left 2–4s gaps.
- **Padding is trimmed.** Supertonic pads every chunk with about 0.55–0.65s of
  silence in front and 0.6–0.7s behind. The server cuts each chunk to its audible
  part (keeping 0.04s) and inserts a 0.45s pause between sentences. Untrimmed,
  sentences were about 1.5s apart.
- The pipeline **exits when playback is done**. Speech-dispatcher then reports
  "end of utterance" and Narrate sends the next paragraph.
- **Stop/skip:** speech-dispatcher kills the client (and the player with it), so
  the socket closes. The server notices before the next chunk and drops the rest
  of that request. A chunk that is already being synthesized finishes first, so
  the next utterance may wait up to one chunk's synthesis time (about 1–3s).
- Requests are handled one at a time (the model isn't shared between threads).
- The socket lives in `$XDG_RUNTIME_DIR` (private to your user). The server and
  client refuse to run without it rather than falling back to a shared directory
  like `/tmp`, where another local user could take over the socket.
- **Protocol**, one request per connection. The client sends one JSON line
  `{"text", "voice", "lang", "rate", "volume"}`. The server answers with frames
  of 1 type byte, a 4-byte big-endian length, and the payload:

  | Type | Payload |
  |------|---------|
  | `A` | audio: mono little-endian float32 at 44100 Hz, one frame per sentence |
  | `D` | done: the whole utterance was sent (empty) |
  | `E` | error: a UTF-8 message; the utterance is incomplete |

  Only `D` counts as success. Without the end frame, a server that failed after
  the first sentence looked exactly like a finished utterance; a connection that
  closes without `D` or `E` is now treated as incomplete too.

Parameter mapping (done in the server):

- `rate` is speech-dispatcher's -100..100 (0 = normal), mapped to Supertonic
  speed 0.7..2.0 (1.05 at 0). Narrate's speed slider changes it.
- **Language comes from the voice name** (`M2-nl` → `nl`), and only falls back
  to `$LANGUAGE` for a name without a suffix. Firefox selects a voice by name
  only, and speech-dispatcher then sends `language=en` even for Dutch pages.
  With plain `M2` listed for both English and Dutch, the name always resolved to
  the English entry, so Dutch was spoken with English pronunciation.
- A language like `en-AU` is cut to `en`; languages Supertonic doesn't know become `na`.
- `volume` -100..0 scales the audio; 0 and above is full volume.
- Without `GenericLanguage ... "utf-8"`, sd_generic recodes text to ISO-8859-1,
  and curly quotes, dashes and non-Latin text arrive as `?`.

## Voices

Supertonic has five female (F1–F5) and five male (M1–M5) voices, and each can
speak every supported language. `install.sh --languages "en nl"` lists each voice
once per language: `F1-en` … `M5-en`, `F1-nl` … `M5-nl`.

Each voice also has a unique private-use language tag (`nl-x-m2`, `en-x-f1`).
On Linux, Firefox's Narrate menu ignores the voice name and labels a voice only
as `<language> (<tag>)` (`_createVoiceLabel` in Firefox's
`modules/narrate/NarrateControls.sys.mjs`). With plain `nl`, all ten Dutch voices
showed up as "Dutch (nl)". Now the menu reads "Dutch (nl-x-m2)" for M2-nl.
*Verified on Firefox 157.0*, as is the need for language-specific voice names. Each
tag needs its own `GenericLanguage … "utf-8"` line; `install.sh` writes them.

Check from a terminal:

```
spd-say -O                          # modules: supertonic, espeak-ng
spd-say -o supertonic -L            # voices
spd-say -o supertonic -y F2-en "Hello"
spd-say -o supertonic -y M2-en "Hello everyone"    # use the -nl, -de, ... voices for other languages
```

Straight to the server, without speech-dispatcher:

```
echo "Hello" | ~/.local/share/speechd-supertonic/supertonic_say.py --voice M2-en \
    | pw-play --raw --format f32 --rate 44100 --channels 1 -
```

## Managing it

```
systemctl --user status supertonic-tts.service    # is the server running?
systemctl --user restart supertonic-tts.service   # after changing supertonic_server.py
systemctl --user stop supertonic-tts.service      # frees ~600 MB; restarts on next request
journalctl --user -u supertonic-tts.service       # startup errors (e.g. uv failures)
```

To restart speech-dispatcher after changing its config:

```
pkill -u "$(id -u)" -x speech-dispatch
```

It's started on demand (by systemd's socket or by a client), so
`systemctl --user stop speech-dispatcher` doesn't always stop it. The next speech
request starts it again with the new config.

## Logging

The server logs every request to `~/.cache/speechd_supertonic.log` (override with
`$SPEECHD_SUPERTONIC_LOG`) and to the journal.

The text being read (web pages, documents) is **not** logged by default, only
its length: `text=<553 chars>`, and `: <57 chars>` for each sentence. Start the
server with `--debug` to log the text as well (`./install.sh --debug` sets that
in the service). The first log line says which mode is on:
`text in log: no, length only` or `text in log: yes (--debug)`. The example
below was logged with `--debug` while reading a Dutch article (`lang=nl`); the
text snippets are translated to English here. The sd_generic command appends
client and `pw-play` errors to the same file, plus a `[player] playback finished`
line when an utterance has actually finished playing.

```
21:20:56,303 [player] INFO playback finished
21:20:56,368 [server] INFO [2] start voice=F1 lang=nl (speechd voice=F1-nl language=en) rate=0 volume=1 text='The folk-ambient mood, ...'
21:20:58,828 [server] INFO [2] chunk 1/4 synthesized in 2.46s (10.32s audio after trimming 0.24s+0.45s silence, 24% of real time), first audio 2.46s after request, ~2.49s silence since previous audio: 'The folk-ambient mood, ...'
21:21:01,071 [server] INFO [2] chunk 2/4 synthesized in 2.24s (8.42s audio after trimming 0.55s+0.71s silence, 27% of real time), ready 8.52s before needed: 'The meandering guitar ...'
21:21:02,564 [server] INFO [2] chunk 3/4 synthesized in 1.49s (5.19s audio after trimming 0.55s+0.66s silence, 29% of real time), ready 15.90s before needed: 'Yet O’Brien stays ...'
21:21:04,273 [server] INFO [2] chunk 4/4 synthesized in 1.71s (6.11s audio after trimming 0.52s+0.76s silence, 28% of real time), ready 19.84s before needed: 'His music unfolds ...'
21:21:04,288 [server] INFO [2] synthesis done: 4 chunks, 31.39s audio in 7.90s; audio should end in ~25.93s
21:21:30,181 [player] INFO playback finished
```

Reading it:

- `start`: `voice`/`lang` are what is actually used; the part in brackets is
  what speech-dispatcher sent. Wrong language? Check which voice is selected in
  Firefox.
- `[n]` is the request number (one per utterance); it restarts at 1 when the
  server restarts. `chunk i/n` is one sentence (very long sentences are split
  further).
- **Silence between paragraphs:** the first chunk's
  `~Ns silence since previous audio`. Almost all of it is the first sentence's
  synthesis (`first audio … after request`). `playback finished` → next `start`
  is speech-dispatcher's overhead (about 0.06s).
- **Gaps inside a paragraph:** every later chunk says either
  `ready Ns before needed` (no gap) or `LATE by Ns (audible gap)`.
- `audio should end in ~Ns` should match the next `playback finished` line to
  within about 0.1s. If playback finishes noticeably later, there were gaps the
  server didn't predict.
- `waited Ns for the previous request`: a new request arrived while an old one
  was still synthesizing (usually right after a stop).
- `stopped by client`: speech was stopped or skipped in Firefox.
- `supertonic_say: can't reach server`: the socket or service isn't running.

### What the timings mean

All times come from log timestamps, not from measuring the speaker, so they are
**estimates** of what you hear:

- "first audio" is when the server *sent* the first audio, not when it played.
  Player startup and buffering (not measured) come on top.
- "audio should end in" assumes playback started at the first send and ran
  without interruption.
- `playback finished` is when `pw-play` exited, which is after its buffer has
  played out.

They are good for comparing runs and spotting gaps, not for exact latency. For
real numbers, record the output (for example with a PipeWire loopback) and
measure the audio itself.

`speechd_timing.py` turns the log into a table per utterance:

| Column | Meaning |
|--------|---------|
| `sent` | sentences (chunks) in the utterance |
| `1st synth` | synthesis time of the first chunk |
| `est. gap` | previous `playback finished` → first audio of this utterance sent: roughly the pause between paragraphs |
| `min ahead` | smallest "ready Ns before needed" of the later chunks; positive = no gap inside the paragraph |
| `end vs est` | `playback finished` minus the predicted end; near 0 = no unpredicted gaps |
| `LATE [..]`, `STOPPED` | predicted gaps inside the paragraph; stopped or skipped |

Deeper debugging (turn off afterwards: the logs grow fast and, unlike the
server's default log, contain the full text being read):

- `Debug 1` at the top of `supertonic.conf`: sd_generic logs the exact text it
  receives and how it ran the command, in
  `$XDG_RUNTIME_DIR/speech-dispatcher/log/supertonic.log`.
- `LogLevel 5` in `speechd.conf`: the daemon logs clients, module choice and
  fallbacks in `$XDG_RUNTIME_DIR/speech-dispatcher/log/speech-dispatcher.log`.

## Known limits

- The server uses about 600 MB of RAM while running.
- Pitch is ignored. Supertonic has no pitch control.
- Silence between paragraphs is the synthesis time of the paragraph's first
  sentence: on the test machine (estimated from the log) about 0.6–1s for short
  ones and 2–4s for long ones. It can't be prefetched, because speech-dispatcher
  only sends the next paragraph after the previous one has finished playing.
  `supertonic_server.py --first-steps 4` synthesizes first sentences with fewer
  quality steps to shorten this (not yet evaluated by ear). To try it, add
  `--first-steps 4` to `ExecStart` with `systemctl --user edit --full supertonic-tts.service`.
- Timing figures in this document come from one machine (see the README) and
  are log-based estimates (see [What the timings mean](#what-the-timings-mean)).
- Narrate uses one voice per page, so English text on a Dutch page (including
  Firefox's own "6–8 minutes" reading-time line) is read with the Dutch voice.
- `SAMPLE_RATE` (44100) is hard-coded in the server and in the `pw-play` command.
  The server refuses to start if the model's rate is different.
